1. Big Picture

This is a small PHP portfolio site with a basic content management module. The public page is served by index.php. Content comes partly from the database, especially the About Me text and color settings. There is also a separate content manager at cmmodule.php that lets an authenticated user update some of that content.

Primary Purpose

Display a personal portfolio page with an editable About Me section.

Main Stack

PHP 8.2, Apache, MariaDB, BrowserSync, Docker Compose.

Main Entry Points

index.php, cmmodule.php, and process.php.

Current State

Runs in Docker and supports live reload for development, but several app features are still partially implemented.

The codebase is not structured as MVC. Presentation, data access, and control flow are mixed directly inside the PHP files. That is the single most important thing to know before you read the code.

3. Request Flow

The easiest way to understand the code is to follow the request paths.

Public site flow

1. Browser requests index.php PHP loads the constants, helper functions, and database connection helper.
2. index.php opens a database connection The page calls getDbConnection() from includes/db.inc.php.
3. About Me content is loaded generateAboutMeParagraphs() reads rows from the aboutme table.
4. Static sections render The image gallery, resume table, and contact form are mostly hard-coded HTML.
5. Footer is appended footer.inc.php prints footer content and the live reload client script.

Content manager flow

1. User opens cmmodule.php The page includes helper files and immediately renders the login form using create().
2. Login is submitted through GET userName and passWord are checked with a simple regex and compared against the database.
3. On success, edit UI is built in JavaScript editpage() injects a color picker, textarea, and submit button into the DOM.
4. process.php stores updates If colorpicker and para1 are present in the query string, the page updates the database.
5. index.php shows updated content The public page reflects database changes on the next load.

Condensed runtime map

User browser
  -> index.php
     -> includes/define.inc.php
     -> includes/dynamic.inc.php
     -> includes/db.inc.php
     -> MariaDB

User browser
  -> cmmodule.php
     -> process.php
     -> includes/dynamic.inc.php
     -> includes/db.inc.php
     -> MariaDB

4. Runtime, Docker, and Hot Reload

The project no longer depends on XAMPP. It now runs through Docker Compose with three services.

Service Technology Responsibility Default Port
web PHP 8.2 + Apache Serves the PHP app from the project root. 8080
dev Node 20 + BrowserSync Watches source files and triggers browser refresh. 3000 / 3001
db MariaDB 11.4 Stores app data and seeds it from SQL on first startup. 3307

Docker entrypoint

docker compose up --build starts all services.

Primary app URL

http://localhost:8080

Live reload URL

http://localhost:3000

BrowserSync UI

http://localhost:3001

How hot reload works

The code is bind-mounted into the containers. That means file edits on the host are immediately visible inside the PHP and Node containers. BrowserSync watches PHP, JS, CSS, and HTML files. The app emits a client script URL through the LIVE_RELOAD_URL environment variable, and the script gets injected into the rendered page through the footer and content manager page.

Important environment variables

Variable Meaning
DB_HOST Database host for PHP to connect to.
DB_PORT Database port used by the application.
DB_NAME Database name, defaulting to a09_jenkins.
DB_USER Database username.
DB_PASSWORD Database password.
WEBSITE_URL Base URL exposed to the PHP app.
LIVE_RELOAD_URL BrowserSync client script used for live reload.

5. Database and Seed Data

The active database dump is sql/a09_jenkins.sql. Docker mounts that file into MariaDB on first startup, which creates the schema and inserts initial rows.

Table Columns Used for
aboutme aID, aPara1 Stores the three About Me paragraph rows shown on the public page.
colors cID, cName, cBlockNo, cHexColor Stores color values for UI sections. Only some of this is actively used.
users uID, uName, uPass, uTimeStamp Stores content manager credentials.

Seeded content that matters right now

  • The About Me table has three rows. The first row starts empty, while rows 2 and 3 contain placeholder text.
  • The Colors table contains default section colors such as black for Menu and blue for About Me.
  • The Users table contains one login: username ben and password jenkins.
Passwords are stored in plain text. That is acceptable for a class exercise or prototype, but not for a production system.

6. Front End and UI Behavior

Styling

The UI uses W3.CSS from the public CDN and relies heavily on utility classes from that library.

Images

The gallery and avatar are static image files stored in the images/ directory.

JavaScript

Most JavaScript is inline inside the PHP pages. The dedicated js/script.js file is currently unused.

Editing UI

The content manager builds its editing controls dynamically in JavaScript after successful login.

Client-side behavior worth knowing

  • validateForm() in index.php validates the contact form client-side, but the form currently posts to /action_page.php, which is not part of this repo.
  • resumeGen() appears intended to fetch resume data with XHR, but it points to resume.json, while the actual file is json/resumemodded.json.
  • The resume section on the page is currently mostly hard-coded HTML, not generated from the database or the JSON file.
  • The content manager's editing controls are created by string-building a block of JavaScript and echoing it from PHP.

7. Maintainer Notes: What Is Incomplete or Risky

Implemented but rough

  • The public About Me section is genuinely database-driven.
  • The Docker runtime and live reload setup are functional.
  • The content manager can update the About Me background color and one paragraph field.

Incomplete or stubbed work

  • generateMainContent() is a TODO and is not used.
  • generateColor() is empty.
  • generateResumeItem() and storeResumeItem() are TODOs.
  • js/script.js exists but is empty.
  • json/resumemodded.json exists, but the current page does not consume it correctly.
  • There are additional SQL dump files in sql/ that are not part of the current Docker startup path.

Architectural and security issues

  • Queries are built with direct string interpolation instead of prepared statements, which creates SQL injection risk.
  • Authentication uses GET parameters and has no session persistence.
  • Passwords are stored as plain text in the database.
  • The helper loginCredentials() ignores its parameters and reads directly from $_GET.
  • storeAboutMeParagraphs() always updates row aID = 1, so only one paragraph is editable through the current implementation.
  • The code mixes HTML, SQL, JavaScript, and control logic directly in the same files, which makes maintenance harder.

Recommended reading order

  1. Read index.php first to understand the public page.
  2. Read includes/dynamic.inc.php next to see where the database interactions live.
  3. Read cmmodule.php and process.php together to understand the content manager.
  4. Read docker-compose.yml, Dockerfile, and package.json last to understand local development and deployment.
If you ever decide to refactor this project, the most defensible first step is to separate database access from rendering and replace raw SQL string interpolation with prepared statements.
